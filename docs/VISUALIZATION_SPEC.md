# MechWorld Explorer: Scientific 3D Viewer and Model Access

## 1. Product goal

A scientist should open a shared demonstration, understand what is being simulated, inspect a specific glycan or crosslink, compare the learned model against LAMMPS, change a permitted loading/intervention scenario, and export the evidence behind the display. This is a research instrument, not a decorative animation.

The required final release includes an easily opened prerecorded browser demo **and** a local model-inference path. Public hosting is gated on data/code rights and Mohammad's approval; a local static bundle satisfies software delivery before hosting approval. A rendered movie alone does not satisfy model access.

## 2. Three scientifically distinct geometry modes

### A. Native patch mode — required first

Render the actual 2D solver positions on a plane in a rotatable 3D scene. Preserve the simulation cell, physical edges, and periodic-image relationships. Use exact stored positions and values, with no cosmetic displacement. Show a scale bar, axes, units, source badge, and loading-step indicator.

A data file generated by the network generator is an **unrelaxed generated network** until a solver run establishes otherwise. Never label it “LAMMPS result” merely because its file format is compatible with LAMMPS.

### B. Cylindrical embedding mode — required, clearly labeled

This maps a planar patch onto a curved surface for interpretation. It does not add solved out-of-plane forces or prove cell inflation.

With the verified source convention `x = axial`, `y = hoop`, a representative mapping is:

```text
theta = (y - y_center) / R
display_position = (x, R*cos(theta), R*sin(theta))
```

Obtain R from a user-declared or measured radius and display its source. A small patch usually covers only an arc. Do not turn a 50-nm patch into a complete micrometer-scale sacculus without declaring repetition or rescaling. A “full-cell overview” can tile a patch or use schematic surface context only when those portions are explicitly labeled as repeated/schematic and never counted as independent simulated data.

For high-shear/nontrivial material mapping, specify reference-coordinate versus current-coordinate embedding and validate its distortion. Compute strain/tension from solver geometry, not from display-space chords. Curved bonds should use appropriate segmented paths rather than chords through the cylinder interior. Periodic seams must be split or drawn using correct ghost endpoints; do not connect axial-periodic endpoints across the whole visible cell.

Show a persistent badge: **2D mechanics displayed on a cylinder; not a 3D mechanical simulation.**

### C. Native 3D mechanics mode — supported in the release

Render actual x/y/z data from the experimentally validated shell/contact observation model, and from a future direct 3D PG simulator if implemented. Identify the solver, mesh/PG representation, pressure boundary conditions, and bending/contact assumptions. Do not generate fake z-displacements from stress colors or pretend direct sacculus simulation exists because this view exists.

The selected full AFM-validation route requires a validated observation calculation, which can be a homogenized shell model. A complete molecular-resolution 3D PG sacculus simulator is a separate extension, not a prerequisite for an honest 3D viewer of the existing 2D work.

## 3. Interface layout

**Top bar:** project/run name, source and checkpoint IDs, geometry mode, physical dimension, units, dataset access label, validation/OOD status.

**Main canvas:** orbit/pan/zoom, reset, scale bar, selectable bonds/nodes, clipping, ghosts, event markers, camera presets.

**Comparison mode:** synchronized LAMMPS/reference and learned-model panels, same camera, same field scale, same physical loading coordinate. A difference view displays meaningful paired quantities only where IDs/alignments permit it.

**Bottom timeline:** play/pause, step, speed, accepted-state markers, rupture events, applied intervention markers, and loading-coordinate labels. Show physical time only for physically timed data. Never interpolate topology through a rupture; optional coordinate interpolation is display-only and labeled.

**Inspector:** selected node/bond ID, molecule and current component, endpoint IDs, rest/current length, tension, energy, state, relevant event probability, units, and source frame. Distinguish a true zero from missing/inactive data.

**Analysis panel:** tension–strain curves, energy terms, intact bond fraction, rupture count, predicted confidence intervals, observed failure endpoint, and error summaries. Clicking a curve locates the matching state without treating two cascade frames as duplicate times.

## 4. Required scientist workflows

1. Open the bundled small real LAMMPS trajectory without installing Python.
2. Load an exported local scene/trajectory without transmitting it to a server.
3. Inspect an intact-to-damaged trajectory and identify the rupture event and subsequent redistribution.
4. Compare a genuine closed-loop model rollout with reference data and view deviations.
5. Select a state, prescribe a local weakening/removal or new load schedule, and request a model counterfactual branch.
6. Optionally launch an authorized reference solver job for that branch; distinguish pending, predicted, and computed results.
7. Sample multiple stochastic rollouts and inspect probabilities without conflating one sample with an expectation.
8. Export raw values/metadata, a reproducible camera/field scene, an image or movie, and a static 3D representation where useful.
9. Load the released checkpoint through Python/CLI and reproduce the same prediction shown in the viewer.

User-drawn interventions are *prescribed actions*. They must not be counted as successful model-predicted failures. A replay of a stored trajectory is *playback*, not live inference.

## 5. Data/visual identity requirements

Mandatory source labels: `generated_unrelaxed`, `lammps_reference`, `model_closed_loop`, `model_teacher_forced`, `experimental_measurement`, `shell_3d_result`, and `illustrative_embedding` as applicable. Geometry and data-source labels are separate fields.

Every displayed physical value traces to a run/frame/ID, field definition, unit, and source checksum. Render IDs through an explicit instance-ID map; instance ordering can change after rupture. Never use GPU instance index as permanent scientific identity.

Fixed reference/prediction color scales are the default. Provide accessible palettes, texture/shape or line-style alternatives, visible missing-data encoding, and physical legends. “Stress” requires a specified stress or tension convention. A thin wire's color must not silently switch from force to strain between views.

Opacity/width exaggeration is permitted for communication but labeled as display styling. Display thickness is not a measured cell-wall thickness. Optional level-of-detail changes cannot alter reported physical counts or silently remove failure hotspots.

## 6. Implementation choice

Recommended first stack: TypeScript browser app with Three.js for geometry and a lightweight chart component; Python inference package/service sharing the same data contracts. Instanced meshes or batched segments avoid a separate scene object per particle/bond [S16]. Do not add a large application framework or authentication system until a concrete deployment need requires it.

Bundle all runtime assets and a small real reference example for a self-contained local/static demonstration. Browser rendering consumes versioned typed arrays with a small JSON metadata manifest, not giant nested Python-object dumps. Export derived browser chunks from canonical HDF5; keep exact source IDs and hashes.

Provide an offline single-file HTML demo for a small selected trajectory if feasible, and a local static-server bundle for full functionality. Test actual offline behavior; a Plotly/Three.js CDN link is not an offline bundle. Document which launch method is required because browser file-access restrictions can prevent large local datasets from loading directly via `file://`.

Offer an independently checkable export to OVITO/VTK-compatible tools, and verify ID/bond preservation on a fixture [S17]. A static GLB/glTF export can aid presentation, but include a metadata sidecar with physical units, scale transformation, source hashes, and a notice that static geometry does not package the dynamics model.

## 7. Local inference/API boundary

Proposed endpoints to implement only after the CLI/checkpoint path works:

```text
GET  /v1/models                       # available verified local model bundles
POST /v1/rollouts                     # validated bounded request → job ID
GET  /v1/jobs/{id}                    # status, cancellation/error reason, progress
GET  /v1/jobs/{id}/result             # authorized generated trajectory
POST /v1/jobs/{id}/cancel             # stop only the caller's owned job
```

Default bind is loopback, not all network interfaces. Model requests accept typed state/control data or authorized local artifact IDs, never arbitrary shell commands or unrestricted filesystem paths. Limit graph size, horizon, event count, uploaded bytes, and execution time. Reject malformed, nonfinite, incompatible, or unsupported parameter states with an actionable error. Do not load arbitrary uploaded Python models.

Keep a run registry for de-duplication and resume. Public read-only demonstration needs no GPU service. Public interactive inference requires explicit approval, quotas, access controls, and a privacy review; it is not silently provisioned by the agent.

## 8. Performance and accessibility targets

Provisional targets, to measure rather than claim in advance:

- Small bundled trajectory opens within five seconds on the declared reference laptop/browser.
- Orbit and playback target 30 frames/second for a representative 10,000-node/15,000-bond scene; report actual dataset size, hardware, and measured frame time.
- Large trajectories stream/cache chunks rather than loading the entire study into browser memory.
- Visible progress, pause/cancel, keyboard access, readable labels, reduced-motion playback, and an explicit “too large” fallback.
- Baseline Windows Chrome/Edge test and at least one other supported desktop/browser combination; record actual coverage.

## 9. Required tests and acceptance evidence

Geometry tests: translated/rotated views, positive/negative skew cells, seam crossings, no false long bonds, cylindrical axis agreement, and round-trip node/edge identity.

Scientific tests: picked values equal exported source values; broken bonds disappear at the correct event; no future information is shown as prediction; camera/LOD does not change statistics; no physical-time labels for minimization states.

End-to-end browser tests: load real fixture, choose field, move timeline, select known edge, compare model/reference, launch local bounded rollout, handle invalid input, export and reopen a scene.

Usability: ask at least one lab scientist other than the developer to identify the source mode, a high-tension region, a failure event, and whether a scene is genuinely 3D-simulated. Record where they misunderstood the UI and fix it. This review requires a real person; an agent-generated favorable review is not evidence.

Final evidence: screenshots/videos from actual runs, automated test logs, a performance report, artifact hashes, and the scientist review record. A polished landing page without these capabilities is not completion.
